# AGENTS.md

Single-crate Rust project (edition 2024): a Raft-replicated order-book matching engine built on OpenRaft.

## Commands

- Build and run one node: `cargo run --bin matchengine-raft -- --id 1 --http-addr 127.0.0.1:21001`
  - The HTTP API stays on `--http-addr`; Raft peer RPCs are gRPC on the same host at `port + 1000`. There is no `--transport` switch.
  - `--data-dir` (env `RAFT_DATA_DIR`, default `/tmp/matchengine-raft`) and `--instance-prefix` (env `RAFT_INSTANCE_PREFIX`, default `matchengine`) place durable state in `<data-dir>/<prefix>-<id>/{log,snapshot}`.
  - `--match-event-log <file>` (env `MATCH_EVENT_LOG`) appends every applied fill/rest/cancel to a JSONL file. Debug aid only: node-local, not replicated, duplicates lines when the log is replayed after a restart. The durable feed is the replicated event log served by `/events`; `--max-events` (env `MAX_EVENTS`, default 262144) bounds it.
  - `--market-data-log <file>` (env `MARKET_DATA_LOG`) enables the deterministic market-data feed (`src/market_data/`) and appends its messages as JSONL. Leader-only by default; `--market-data-depth`, `--market-data-status-every`, `--market-data-bar-intervals-ms` and `--market-data-leader-only` tune it.
  - `RAFT_CORE_WORKERS` >0 runs OpenRaft on a dedicated multi-threaded runtime (`raft-worker`) with that many workers; unset or 0 keeps Raft on the shared runtime. HTTP, gRPC and the market-data feed stay on the main runtime.
  - `RAFT_WAL_FSYNC_MS` controls WAL fsync: unset = no fsync (default), `0` = fsync every append, `N > 0` = periodic fsync every N ms on a Tokio `wal-fsync` task (the blocking `sync_data` runs on `spawn_blocking`). Unset also sets `min_voters = 4` in the binary: `/init` and `/change-membership` reject fewer voters and writes return `503` until four voters exist. Demo scripts default `RAFT_WAL_FSYNC_MS=0` so their three-node/single-node setups remain valid.
  - `--read-policy <lease|read_index>` (env `MATCHENGINE_READ_POLICY`, default `lease`) controls leader-consistent reads; lease mode falls back to `ReadIndex` when the lease is stale and requires bounded clock drift. Use `read_index` to force a fresh quorum round. `/read` stays local.
  - `--max-inflight-writes <N>` (env `MATCHENGINE_MAX_INFLIGHT_WRITES`, default 1024) caps concurrent `/write` and `/write_batch` requests per node; excess requests get `429`, and `0` disables rejection. `512` is the tighter-tail setting. `GET /admission/status` reports limit, in-flight, peak, admitted and rejected counters.
  - Production profile: no fsync plus at least four voters for maximum throughput, or `RAFT_WAL_FSYNC_MS=0` for durable writes; keep the OpenRaft `300/1/0` defaults, shared runtime and default build profile; use `/write_batch` at 32-128 orders; the server enforces 1,024 in-flight `/write`/`/write_batch` requests by default (`512` for a tighter tail, `0` disables); lease reads are the default, so set `read_index` when clocks are not bounded. See `docs/PERFORMANCE.md#production-configuration-decisions-2026-11-08`.
  - `--async-wal` (env `MATCHENGINE_ASYNC_WAL`) enables the prototype async WAL. It requires `--features async-wal` and `RAFT_WAL_FSYNC_MS=0`; off by default.
CI (`.github/workflows/ci.yml`) runs `cargo fmt --all -- --check` (and the `fuzz/` crate's fmt check), `cargo clippy --all-targets -- -D warnings` and `cargo test` on push/PR, plus an `async-wal` job (feature Clippy and crash-recovery tests), a `profiling` job (feature Clippy and the `/metrics` runtime-stats test), a `bench-regression` job (`apply_path --check`, `book_replay --check`, `replay_mix --check`), the standalone `demos/order_system/` crate's fmt, Clippy and `--locked` test run, and an `msrv` job that runs `cargo check --all-targets --locked` on Rust 1.89 to enforce `rust-version`. `.github/workflows/bench-linux.yml` is a manual `Linux benchmark` workflow for the pinned-core short and sustained `e2e` pass. `Cargo.lock` is tracked (do not add it back to `.gitignore`).
- `cargo test` runs everything (a single integration target, `cluster`, ~10s once built). Focus it with `cargo test --test cluster`. The feature-gated async WAL tests run with `cargo test --features async-wal --test cluster async_wal`.
  - `cargo +nightly fuzz build` builds the separate `fuzz/` cargo-fuzz crate (`order_book`, `wal_decode`, `snapshot_decode`, `wire_decode`); `.github/workflows/fuzz.yml` builds it nightly and runs a short smoke pass. The fuzz crate is outside the root workspace so stable `cargo test` and clippy do not compile libFuzzer.
  - `cargo bench --bench matchengine` runs the order-book micro-benchmarks (no framework, prints best-of-5 per-round times).
  - `cargo bench --bench book_replay` exercises `OrderBook` directly with deep sweeps, deep cancels and BBO-advance/query cases; no HTTP, Raft, WAL or feed. `benches/bench_support` clones before the timer and drops after it, and every case reports best-of-5 plus warm p50/p99 and an interleaved cold pass (64 MiB eviction sweep). `--check` enforces the loose warm p50/p99 CI bounds from `docs/PERFORMANCE.md`; cold passes stay informational. Results live in `docs/PERFORMANCE.md`.
  - `cargo bench --bench replay_mix` replays a deterministic 100,000-operation add/cancel/amend/stop/iceberg/taker fixture with maker/taker fees through `OrderBook` directly; it reports whole-replay warm/cold p50/p99 and per-operation p50/p99/max by kind. `--check` enforces the loose whole-replay warm p50/p99 CI bounds. Results live in `docs/PERFORMANCE.md`.
  - `cargo bench --bench level_book` compares the bench-only per-price-level bucket prototype with `OrderBook` on match, cancel, sparse/dense amend, depth and BBO workloads; it verifies both books against each other before timing and reports warm/cold p50/p99 with the p50 ratio as the headline. Results and the adoption conclusion live in `docs/PERFORMANCE.md`. The prototype is not production code.
  - `cargo bench --bench e2e` starts a single node (127.0.0.1:24002 on the default multi-thread runtime) and measures HTTP submit → Raft commit → apply → response, including a `/write_batch` sweep at 1/8/32/64/128 orders per entry plus concurrent batches; pass `-- current` or `-- both` to compare the main runtime flavor (OpenRaft stays on whichever runtime `RAFT_CORE_WORKERS` selects), `RAFT_WAL_FSYNC_MS` to select the WAL fsync mode for the benchmark, `MATCHENGINE_ASYNC_WAL=1` with `--features async-wal` and `RAFT_WAL_FSYNC_MS=0` to select the prototype async WAL, and `--pin <cpu>` to pin the process on Linux (`sched_setaffinity`; macOS fails loudly because it has no core-pinning API). `--duration <seconds> --clients <n>` replaces the short suite with a sustained closed-loop write load (`--clients` defaults to 64 and requires `--duration`) and reports process CPU from `getrusage` plus one-second interval samples; the node is in-process, so monitor the bench process, not a separately started binary. Results live in `docs/PERFORMANCE.md`.
  - `cargo bench --bench cluster_e2e -- --rounds 3` starts four in-process loopback voters (HTTP 25101-25104, gRPC 26101-26104), initializes all four, disables WAL fsync and measures leader-direct writes and batches over a fresh cluster each round. The client runs on a separate runtime. `--concurrency-only --clients 1,8,64,256,1024,4096` runs the concurrency sweep; `--preconnect` establishes one keep-alive connection per client before the timed burst; `--max-inflight-writes N` sets the admission gate for the run (0, the benchmark default, measures the unbounded path); `--max-payload-entries`, `--purge-batch-size`, `--api-batch-linger-ms` and `--snapshot-logs` expose one-factor OpenRaft sweeps. `RAFT_CORE_WORKERS` and `CARGO_PROFILE_BENCH_LTO`/`CARGO_PROFILE_BENCH_CODEGEN_UNITS` select the runtime and build-profile A/Bs. `--help` prints the flags plus flamegraph/tokio-console guidance. `--features profiling` enables OpenRaft runtime histograms and makes the leader's `/metrics` include `runtime_stats`. Results live in `docs/PERFORMANCE.md`.
  - `cargo bench --bench read_e2e -- --policy read_index|lease|both` starts the same four-node no-fsync cluster on a server runtime and runs local `/read`, `/linearizable_read` and `/events` from a separate client runtime at 1/64 readers, read-only and mixed with paced writes. Results live in `docs/PERFORMANCE.md`.
  - `cargo bench --bench storage` measures WAL append/read/reopen with real order payloads; `RAFT_WAL_FSYNC_MS` selects the fsync mode (unset = none, `0` = every append, `N` = periodic). `MATCHENGINE_ASYNC_WAL=1` with `--features async-wal` and `RAFT_WAL_FSYNC_MS=0` runs the prototype async path. Results live in `docs/PERFORMANCE.md`.
  - `cargo bench --bench p0_bench -- duplicate|read|snapshot` measures the P0 state-machine optimizations: duplicate retry scan, large reads under write load, and snapshot under write load.
  - `cargo bench --bench apply_path` drives `StateMachineStore::apply` directly with a counting global allocator and reports heap allocations/bytes per applied entry for blank, rest, cancel, fill and 128-request batch workloads. `--check` enforces exact allocation-count ceilings (fewer passes, more fails) plus a small requested-bytes allowance; the `bench-regression` CI job runs it. Results live in `docs/PERFORMANCE.md`.

## Where things are wired

- `build_match_engine_node()` in `src/lib.rs` is the only composition point: it opens `LogStore`/`StateMachineStore` from a `StorageConfig`, creates the Raft config, `GrpcNetworkFactory`, binds the gRPC listener, starts the tonic server and registers every actix route. When `RAFT_CORE_WORKERS` is positive it builds Raft with `Raft::build` and runs it on a dedicated multi-threaded runtime (`RaftThread`, that many workers); otherwise it uses `Raft::new` on the shared runtime. It returns a `MatchEngineNode` whose `run()` waits for shutdown and whose `shutdown()` stops HTTP, gRPC, Raft and the dedicated runtime cleanly (needed before reopening the same storage).
- The binary runs on a multi-threaded Tokio runtime (`#[tokio::main(flavor = "multi_thread")]` in `src/main.rs`); Actix HTTP workers are separate threads. With `RAFT_CORE_WORKERS` >0, OpenRaft's RaftCore and state-machine worker run on the dedicated `raft-worker` runtime, so `apply` no longer competes with HTTP/gRPC/feed tasks, though it can still migrate between the dedicated workers; unset or 0 keeps the shared-runtime behavior. `spawn_blocking` is reserved for WAL/snapshot/file-sink I/O and startup recovery: `LogStore::open` and `StateMachineStore::open` run there, `FileLogSink` opts into `spawn_blocking` via `MatchResultSink::is_blocking`, and `JsonlSink` uses a Tokio writer task over `tokio::fs`. See the thread/task audit in `docs/PERFORMANCE.md`.
- Match-result processing is pluggable: `src/match_result/mod.rs` defines `MatchEvent`/`EventId` and the `MatchResultSink` trait (`NoopSink`, `MemorySink`, `FileLogSink`). `build_match_engine_node` installs `NoopSink`, or a `FileLogSink` when `StorageConfig::match_event_log` is set, via `StateMachineStore::open_with_sinks_and_retention`. `apply` derives events from the entry alone, appends them to the replicated event window, returns the first 512 in `/write`, and collects sink/tap work in `PendingPublish`; the state-machine lock is acquired per entry and the sink/tap publishing runs after it is released. The per-entry event buffer and publish list are inline `SmallVec`s for the common small case (a large sweep spills to the heap), and fills/rests are written directly into that buffer. Sink errors are logged and never fail the apply. `POST /events` serves the window with an `(log_index, ordinal)` cursor; `GET /events/status` reports retention. `Place { client_order_id }` dedupes retries through a fixed 262144-record map (`MAX_SUBMISSIONS`), kept independent of `--max-events` so retry resolution cannot diverge across nodes.
- `MatchEngineRequest::Batch { requests }` applies 1–128 non-nested requests in one entry (one WAL append/fsync): sub-requests run in order, each keeps its own sequence/response under `MatchEngineResponse.batch`, and event ordinals continue across the whole entry. `/write_batch` takes a bare JSON array; empty, nested, oversized and duplicate-`client_order_id` batches are rejected at the edge.
- `start_match_engine_node_with_config()` and `start_match_engine_node_with_storage()` are thin build+run wrappers for the binary, tests and benchmarks.
- Actual HTTP routes: `/init`, `/add-learner`, `/change-membership`, `GET /metrics`, `/get_linearizer`, `GET /read-policy/status`, `/write`, `/write_batch`, `/read`, `/linearizable_read`, `/follower_read`, `POST /events`, `GET /events/status`, `GET /admission/status`, `GET /health`, `GET /ready`, `/console`, `/console/`, `/console/api/node`, `/console/api/cluster`, `/console/api/actions`, `/console/api/actions/transfer-leader`, `/console/api/actions/elect`, `/console/api/actions/snapshot`. Raft RPCs are gRPC-only; there are no HTTP `/append`, `/vote` or `/snapshot` routes.
- `/write` and `/write_batch` run a leader-side symbol guard before `client_write`: a `Place`/`Cancel`/`Amend` whose `symbol_id` differs from the applied `symbol_config` is rejected with `400`, so it costs no log entry, sequence or `rejected` event. Followers skip the guard so forwarding still works; requests after a `ConfigureSymbol` in the same batch are left to the state machine, which still re-checks the symbol.
- Leader-consistent reads default to `Lease` (`src/network/read_policy.rs`). `/linearizable_read`, `/events`, gRPC `StreamEvents` and `/get_linearizer` try `ReadPolicy::LeaseRead` and fall back to `ReadIndex` when the lease is stale; `--read-policy read_index` (env `MATCHENGINE_READ_POLICY=read_index`) forces a fresh quorum round. `GET /read-policy/status` reports per-path lease/fallback counters. Lease reads require bounded clock drift; `/read` remains local and unaffected.
- `src/client.rs` is the leader-aware HTTP client. `ClientConfig` sets the request timeout, transient retries and forward retries with exponential backoff; `ClientError` distinguishes HTTP edge rejections (`Api`), no known leader, timeouts, decode failures and Raft transport errors. Transient retries are at-least-once; set `client_order_id` on writes that must not duplicate. `tests/cluster/test_client.rs` covers typed no-leader/API errors, retry after a dropped connection and forwarding after leader failover.
- `src/network/health.rs` serves `GET /health` (liveness: gRPC listener flag, Raft running state, WAL and state-machine frontier) and `GET /ready` (healthy plus a known cluster leader). `MatchEngineApp` carries the `LogStore` and a shared `GrpcListenerHealth` flag; the gRPC task clears the flag when its server future exits.
- `GET /metrics` (in `src/network/management.rs`) keeps the `RaftMetrics` fields flattened at the top level for existing clients and adds `data_metrics`, `server_metrics` and `runtime_stats`. OpenRaft runtime histograms are compiled only with `--features profiling`; without it `runtime_stats` is `null`. The profiling feature is CI-checked and the histogram string is the compact `RuntimeStats { ... }` display.
- `src/network/console.rs` serves the embedded `/console/` WebUI and `/console/api/*`: a stable node snapshot, a server-side cluster aggregate (membership addresses only), and guarded transfer-leader/election/snapshot actions. Actions require `X-Console-Action`, are serialized by one lock, and are logged. Graceful transfer uses the gRPC `TransferLeader` RPC.
- gRPC Raft service (`proto/raft.proto`, `src/network/grpc/`): `AppendEntries`, `Vote`, `PreVote`, `InstallSnapshot` (client-streaming chunks), `AppendStream` (bidirectional, used by `stream_append`) and `TransferLeader` (leadership handoff). Envelopes are protobuf; Raft payloads are `postcard`-encoded openraft types. The same listener serves `EventService.StreamEvents` for match-event streaming; its page payloads are JSON (`EventsResponse`), not postcard, because `MatchEvent` uses `skip_serializing_if` for absent optional fields.
- Pre-Vote is enabled (`default_raft_config` sets `enable_pre_vote: Some(true)`) and carried by the dedicated `PreVote` RPC: `src/network/grpc/server.rs` calls `Raft::pre_vote`, and the client implements `RaftNetworkV2::pre_vote`. openraft's default `pre_vote` grants unconditionally, so the RPC is required for the flag to have an effect. There is no mixed-version rolling upgrade: an older peer returns `Unimplemented`, which cannot grant a PreVote.
- Raft port convention: `BasicNode.addr` stays the HTTP API address, and the gRPC Raft transport lives at `raft_addr_from_http(addr)` = same host, port + `RAFT_PORT_OFFSET` (1000). `src/network/mod.rs` owns the derivation.
- `/init` takes a JSON array, so a single-node cluster must be initialised with `-d '[]'`. A bare POST or `-d '{}'` fails deserialization ("invalid type: map, expected a sequence"); all scripts now send `'[]'`.
- `examples/sled.rs` is a playground example (creates a local `my_db` sled dir, gitignored); `sled` is a dev-dependency, so it is not linked into the node binary.
- `cargo run --example dump_wal -- <node-dir|log-dir|segment.wal>` and `cargo run --example dump_snapshot -- <node-dir|snapshot-dir|current.snap>` print read-only, CRC-validated JSONL dumps of durable state. `read_wal_file` and `read_snapshot_file` are the public helpers behind them; `read_wal_bytes` and `read_snapshot_bytes` are the pure byte decoders the fuzz targets use.
- `cargo run --release --example replay_orders -- --orders orders.jsonl [--expected expected.jsonl]` starts an in-process node, replays orders in `/write_batch` batches, and compares the generated match-event JSONL (ignoring `node_id`/`log_index` unless `--strict-log-index`). `cargo run --release --example replay_orders_events -- ...` replays the same input and compares events read from the replicated `POST /events` API instead of the local sink; `--events-limit` controls paging.
- `./tests/replay/run-all.sh` runs the checked-in replay matrix. Each `tests/replay/<case>/` directory has `orders.jsonl`, `expected-events.jsonl`, `run.sh` and a scenario `README.md`; cases cover GTC, IOC, FOK, GTD, Day, market, post-only, iceberg, stop-market, stop-limit, amend, cancel, default-policy maker/taker fees, quote-asset fees, fee overflow and an overflow that leaves a base fee exact. Default HTTP ports are `24211`–`24226` (gRPC port +1000), one per case. `./tests/replay/run-all.sh events` runs the same cases through `replay_orders_events` and `POST /events` on one sequential address (`EVENTS_REPLAY_ADDR`, default 24202); `EVENTS_LIMIT` exercises pagination. Replay cases are manual and not part of `cargo test`.
- `./scripts/market-data-system.sh` builds the engine with `--features market-data-aeron` and the standalone market-data system at `demos/market_data_system` with `--features aeron`, starts two engines with separate embedded Aeron media drivers (IPC): EUR/USD on `127.0.0.1:24801` and BTC/USDT on `127.0.0.1:24802`. One service on `127.0.0.1:24800` consumes both; `http://127.0.0.1:24800/` is a test page whose symbol dropdown switches topics with live `UNSUBSCRIBE`/`SUBSCRIBE` over a single WebSocket (no reconnect). For the driverless fallback, start each engine with `--market-data-log <file>` and run `cargo run --manifest-path demos/market_data_system/Cargo.toml -- --market-data-log <file> --symbol eurusd:0:EUR:USD` (repeat the flag per symbol). The service also runs against multicast channels (`--aeron-channel 'aeron:udp?endpoint=...'`, repeat per symbol) with one instance per host. rusteron is pinned to `=0.2.13` because `0.2.14+` uses an unstable `cold_path` API.
- `cargo run --manifest-path demos/order_system/Cargo.toml -- --addr 127.0.0.1:24300 --engine 127.0.0.1:24301 --engine-id 1` starts the standalone demo order desk. It is a separate crate/process under `demos/order_system/`, talks to an already-running engine over HTTP, and never modifies the engine binary. It also estimates the order-system freeze and maker/taker settlement from the replicated symbol config and fee rates (`demos/order_system/src/freeze.rs`); those figures are labelled demo estimates, not engine balances. The ticket has a demo-only **Perpetual** product with leverage `1..=100`: a linear quote-margined overlay that estimates margin/notional/fee, requires `fee_asset_policy=quote`, and sends an ordinary engine order (product/leverage metadata is demo-process memory keyed by sequence). See `demos/order_system/README.md`.

- **Breaking wire/disk change (2026-10-29):** `Order.price`/`volume`, stop/iceberg fields,
  `OrderBook.last_trade_price`, `MatchEvent.price/volume`, depth/BBO records and the market-data

  `taker_fee`/`maker_fee` plus the fee asset from the order-level user tier. ETF/equity bases
  force `FeeAssetPolicy::Quote`; crypto/spot and fiat-to-fiat pairs default to `Received`.
  Snapshot **v10** and
  wire **v6** are incompatible with older builds; v10 rejects v9. Wipe the node's `--data-dir`

- Upgraded to `openraft` 0.10.0-alpha.37 from crates.io (git pin and the `openraft-legacy` dependency are gone). Installing it is a normal `cargo fetch`; no git checkout needed.
- The node runs **gRPC (tonic) only** for peer-to-peer Raft RPCs; the HTTP/JSON transport was removed.
  - `src/network/grpc/client.rs`: `RaftNetworkV2` implementation with unary append/vote, a custom `stream_append` over `AppendStream`, and chunked `full_snapshot` that honours the `cancel` future.
  - `src/network/grpc/server.rs`: tonic service calling the `Raft` APIs. Its `AppendStream` handler feeds `Raft::stream_append`, so the follower pipelines into RaftCore.
  - `src/network/grpc/client.rs`: also owns `GrpcNetworkFactory`, the only `RaftNetworkFactory` used by `Raft::new`.
- Transport failure mapping: tonic `Unavailable` -> `RPCError::Unreachable` (backoff), `DeadlineExceeded` / elapsed `soft_ttl` -> `RPCError::Timeout`, other statuses -> `RPCError::Network`. Raft-level rejections travel as encoded `RaftError` payloads.
- Message limits: both directions of the gRPC service are capped at 64 MiB (`MAX_MESSAGE_SIZE`); snapshot chunks follow `RPCOption::snapshot_chunk_size()` (OpenRaft default 3 MiB, capped at 8 MiB).
- Public edge: the HTTP API and gRPC listener are plaintext and unauthenticated **by design**; this is an internal matching engine behind a gateway that owns TLS and client authentication. The supported deployment contract is loopback or a trusted private network. Application JSON bodies are capped at 1 MiB, `client_order_id` at 128 bytes from `[A-Za-z0-9._:-]`, `/read` keys at 128 bytes, `/events` pages at 1–1000, gRPC messages at 64 MiB, and snapshot streams at 256 MiB (`src/network/api.rs`, `src/network/mod.rs`, `src/network/grpc/server.rs`).
- Deadlines: unary vote/append and each `stream_append` request in flight get `RPCOption::soft_ttl()`. `stream_append` only times a wait while a request is in flight (the heartbeat worker polls for a response before the feeder necessarily sends), and `full_snapshot` has no per-RPC deadline — it is bounded by the `cancel` future and HTTP/2 keep-alive, because a legitimate snapshot can outlive one heartbeat interval.
- Each peer gets three explicit gRPC channels: replication, heartbeat and snapshot. `GrpcNetworkFactory` overrides `new_heartbeat_client`/`new_snapshot_client` and each `GrpcNetwork` owns its own lazy channel with a role-specific profile, so a snapshot cannot head-of-line-block a vote. Heartbeat uses 256 KiB stream / 1 MiB connection windows; replication uses 1 MiB / 4 MiB; snapshot uses 1 MiB / 4 MiB with 5 s connect and 10 s / 5 s keepalive.
- The gRPC server uses 1 MiB HTTP/2 stream windows, 4 MiB connection windows and 5 s / 3 s keepalive; `full_snapshot` uses OpenRaft's configured chunk size rather than a fixed constant.
- The async WAL prototype (`async-wal` feature) writes the batch and updates the visible log, defers `sync_data` to a Tokio worker and fires `IOFlushed` only after the fsync. Pending entries are served from an in-memory cache; `truncate_after`/`purge` flush pending appends first. It is off by default, requires `--async-wal` plus `RAFT_WAL_FSYNC_MS=0`, and is covered by `test_storage::async_wal_defers_io_flushed_and_recovers_a_lost_tail` and `test_async_wal`.
- Storage uses a hand-written segmented WAL in `src/store/log_store.rs`: `log/NNNNNNNNNN.wal` with an 8-byte `MRFT`+version header, `[len u32 LE][crc32 u32 LE][postcard payload]` records, one `write_all` per openraft append batch plus a configurable fsync policy, `pread` reads, and blocking IO on `spawn_blocking`. Recovery walks segments, rejects index gaps and truncates a torn tail. Vote + `last_purged` live in an atomically rewritten `log/state`; `committed` is a WAL record that becomes durable with the next append (no second fsync). `RAFT_WAL_FSYNC_MS` selects the WAL fsync mode: unset = no fsync (default), `0` = every append, `N > 0` = periodic every N ms. `StorageConfig::wal_fsync` / `with_wal_fsync(...)` carries the same setting for library callers; `StorageConfig::min_voters` / `with_min_voters(...)` carries the voter floor (default 1 for library callers). Non-every-append modes are not fully durable and use best-effort WAL truncation (first corrupt segment/record/index gap, later segments deleted) so Raft can catch up from peers. See `docs/STORAGE.md` for the recovery contract.
- Default snapshots are `LogsSinceLast(100_000)` plus a 30-minute timer; `StorageConfig::snapshot_interval` / `--snapshot-interval-ms` tunes it and `0` disables only the timer. `default_raft_config` sets `replication_lag_threshold = 150_000` (above the snapshot policy) and `heartbeat_min_interval = Some(500)` to suppress redundant heartbeats under sustained replication.
- Storage hot paths: WAL append uses a borrowed encoder, recovery scans segments sequentially, contiguous reads share one `pread`, snapshot encode/write happens outside the state-machine lock, and snapshot bodies stream through an incremental CRC writer. `docs/PERFORMANCE.md` records the baseline.
- A failed or dropped gRPC server task is fail-fast: `MatchEngineNode::run()` stops HTTP and background tasks, shuts Raft down, and returns the error. HTTP requests use one `Logger` middleware.
- `/ready` requires `Raft::wait_for_recovery` to confirm the state machine applied the cluster commit covering the durable log tail; `/health` exposes the `recovered` flag. This covers the deliberately non-fsynced `save_committed` WAL marker without adding a second fsync per commit.
- `src/store/state_machine.rs` keeps the order book + sequence + event window in memory and persists `snapshot/current.snap` (magic `MRFSNAP` + version + postcard meta + postcard content) via temp file → fsync → rename → dir fsync. Snapshot version is 10 (v10 replaces the boolean fee-overflow flag with `MatchErrors`; v3 added the extended `Order`, parked stops and last trade price; v4 added the retained `MatchEvent` window and client-order-id dedupe map; v5 stored prices/quantities as 18-scale `Fixed` integers; v6 stored the last trade price and match events as `Fixed`; v7 added the replicated single-symbol precision configuration; v8 added maker/taker fee rates to orders and fee fields to match events; v9 added base/quote asset metadata, tick/lot rules, volume units and fee assets). Older files are rejected on open. `install_snapshot` validates before replacing the durable copy. Restart = open snapshot, then openraft replays the retained log tail.
- `src/store/config.rs` owns `StorageConfig` (`data_dir`, `instance_prefix`, `node_dir`/`log_dir`/`snapshot_dir`). The old sled-backed `src/store/store.rs` and the `walkdir` dependency are gone; `sled` remains only for the `examples/sled.rs` playground.

## Matching-engine quirks

- `OrderBook::execute_order` is the full lifecycle `apply` runs (validate, park a stop, sweep, rest
  or cancel the remainder, run the stop cascade) and returns an `Outcome`; `place_order` is the
  compatibility wrapper that returns only the fills. `OrderBook::place_order` stops matching as soon
  as the taker's remaining volume reaches zero, and a partially filled maker is updated in place so
  its `id`, `side`, `live` and `sequence` survive. `Order::new` still hardcodes `id: 0`, so do not
  use it to rebuild a resting order. Regression tests: `exact_fill_*`,
  `partial_fill_preserves_maker_identity` in `src/order_book/mod.rs`.
- Order types live as flat fields on `Order` (`tif`, `post_only`, `stop_price`, `display_volume`,
  `hidden_volume`, `timestamp`), all with serde defaults. `stop_price`/`display_volume` use `Fixed::ZERO`
  (JSON `0`) as "none" so the record stays cheap to copy in the matching loop. `apply` never reads a clock:
  every admissible mutating request purges due GTD orders at its intake timestamp; `Day` still needs
  the explicit `PurgeExpired { now_ms, day_close_ms }`. Stops are elected by
  `OrderBook::last_trade_price`, which is replicated state. Parked stops live in
  `orderbook.stops` (admission order, off the book, invisible to depth) and are cancelled by side +
  sequence. A stop child never rests: whatever it cannot execute is cancelled. A stop the last
  trade already crosses is refused (`stop_would_trigger`) rather than firing on entry.
- Rejections (FOK unfillable, post-only crossing, stop already crossed, invalid shape) do not enter
  the book; `apply` publishes a `rejected` event with a `reason` and the write still returns the
  assigned sequence. Event kinds are `fill`, `rested`, `cancelled`, `triggered`, `expired`,
  `rejected`, `amended`; a stop cascade keeps increasing ordinals inside the same log entry.
- The market-data tap does not run on the matching path: book mutations append `DepthChange`
  entries to a transient `OrderBook::depth_journal` (`enable_depth_journal`, `#[serde(skip)]`) and
  `apply` hands the journal plus the entry's `MatchEvent`s to a bounded tokio `mpsc` sender
  (`try_send`). A separate tokio task owns the shadow book, OHLC bars, encoding and the sink. A full
  queue drops frames and emits `GAP`; matching is never blocked. The feed is leader-gated by
  default through a `raft.metrics()` watcher, which pushes a reset snapshot on every leadership
  gain (`--market-data-leader-only=false` publishes from every replica).
- The receiving HTTP node stamps `Order.timestamp` at intake (overwriting client values) before
  proposing; it travels in the log and labels events and market data. `MatchEvent.side` is the side
  of the order the event is about.
- Market-data keys are `(symbol_id, stream_id, market_seq, sub_seq)`. `market_seq` is the replicated
  mutation sequence: `Place` uses the taker order sequence, `Cancel`/`Amend`/`PurgeExpired` each
  consume one, and stop cascades anchor to the electing taker. Boundaries are entry-driven (one
  TRADE per taker with every fill, one depth/BBO per changed entry, status every `status_every`
  sequences), so the key is identical across replicas, failover and restart. `GAP` is diagnostic.
  A takeover snapshot's boundary is the **next** sequence.
- `OrderBook::amend` handles plain resting limits, icebergs and parked stops. A book order is keyed
  like `cancel` (side + current price + sequence); a stop by side + sequence. For a plain limit or
  iceberg, a same-price open-volume reduction keeps the sequence (time priority) and updates in
  place; a new price or a larger open volume re-inserts under a NEW sequence, which the `/write`
  response returns. An iceberg's amended `volume` is its new total open volume: the display tranche
  is preserved, `min(display, volume)` stays visible and the rest becomes hidden. For a parked stop,
  `order.stop_price > 0` is the new trigger (`0` keeps it), `price` updates a stop-limit's limit
  (refused for a stop-market) and the stop keeps its sequence; a trigger the last trade already
  crosses is refused (`StopWouldTrigger`). Crossing book amendments are refused
  (`amend_would_cross`); market orders are cancel + re-place. `OrderBook::spread`/`mid_price`/`depth`
  are read-only views (depth aggregates visible volume only, hidden iceberg reserve excluded).
- `Order` deserializes `sequence` with a default of `0`; the scripts still send it, and
  `place_order()` overwrites it. `Order` equality compares `id`, `side`, `symbol_id`, `sequence`,
  `price` and `volume`.
- Fills compute maker/taker fees from the two orders' user-level `maker_fee_rate`/`taker_fee_rate` (signed fractions of notional). `MatchResult` carries `notional`, both fees and `error` (an ordered `MatchErrors` set); `MatchEvent` carries the fees and error set, and market-data `TRADE`/fill `LIFECYCLE` mirror them. The engine records fees but does not maintain balances: the order system freezes the trading asset and clearing deducts fees from that freeze (`docs/FEE_DEDUCTION.md` §6.6).
- Match results leave `apply` as `MatchEvent`s through a `MatchResultSink`. `EventId` is
  `(log_index, ordinal)`, so no event counter is stored in snapshots; `OrderBook::resting_volume`
  is the authoritative source for a `Rested` event's volume (do not derive it by subtraction).
- A process/cluster trades exactly one symbol. Replicated `StateMachineData.symbol_config` + `symbol_locked` (snapshot v10) hold its precision; `MatchEngineRequest::ConfigureSymbol` updates it through Raft before trading, locks it after the first accepted order, and queues a market-data reset snapshot when the node is publishing. `apply` rejects `Place`/`Amend` values with more decimals than configured and rejects orders with a different `symbol_id`; on the leader, `/write` and `/write_batch` reject a wrong-symbol request earlier, with `400` before the Raft proposal. `/read symbol_config` and `/read symbol_id` expose it. Multi-symbol means one process/cluster per symbol, not multiple books in one process.
- `/read` keys are resolved by `read_state` in `src/network/api.rs`: `orderbook_orders`,
  `orderbook_stops`, `orderbook_last_trade_price`, `orderbook_depth` (`orderbook_depth:N` for N
  levels, capped at 200), `orderbook_spread`, `marketdata_status`, and `orderbook_sequence`
  (misspelled variant `orderbook_sequance` also accepted). Any other key returns an empty string;
  there is no KV store.
